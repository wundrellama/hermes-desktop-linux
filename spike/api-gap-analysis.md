# API gap analysis — hermes-desktop ⇢ SwiftCrossUI v0.6.0 (GtkBackend)

**Decision driver for Phase 0 GO/NO-GO**.

**Inputs**:
- `spike/inventory.md` — every SwiftUI API used in `Sources/HermesDesktop/Views/` (generated by `spike/inventory.sh`).
- `/tmp/swift-cross-ui/` at tag `v0.6.0` — the SwiftCrossUI public API surface (see `spike/swift-cross-ui-decision.md` for the backend rationale).

**Backend pinned**: `GtkBackend` (Gtk4). The plan's assumed Qt6Backend is unmaintained in v0.6.0 — see `swift-cross-ui-decision.md`.

---

## Recommendation: PROCEED, with three caveats

The supported-API surface of SwiftCrossUI v0.6.0 covers ~85% of hermes-desktop's SwiftUI footprint. Gaps are concentrated in three specific places — none are existential, but **two require non-trivial mitigation work** outside the original 20-week budget.

**GO conditions, all true today:**
1. All property wrappers actually used in `Views/` (`@State`, `@Binding`, `@EnvironmentObject`, `@ObservedObject`, `@Environment`, `@SceneStorage`) are supported by SwiftCrossUI.
2. All core layout primitives (VStack/HStack/ZStack/ScrollView/LazyVStack/Group/Section) exist.
3. All input controls used (Button/TextField/Toggle/Picker/Menu/TextEditor/SecureField/DatePicker/ProgressView/Slider/Label/Image/Text/Divider/Spacer) exist.
4. Lifecycle modifiers used (`.task`, `.onAppear`, `.onChange`, `.onSubmit`, `.onTapGesture`, `.onHover`) exist.
5. Modal modifiers used (`.alert`, `.sheet`) exist.
6. Kanban does **not** use SwiftUI drag-drop. Movement is via menus/buttons (confirmed: grep shows zero `.onDrag`/`.onDrop`/`.draggable`/`.gesture(.drag*)` in `KanbanView.swift`). This was the plan's #1 risk and **it evaporates** — the Kanban is structurally portable.

**Three caveats (the work that lives outside the original ~20-week budget):**
- **C1: Apple Charts (UsageView).** Zero of `BarMark`, `LineMark`, `SectorMark`, `AxisMarks`, `AxisGridLine`, `AxisTick`, `AxisValueLabel`, `chartXAxisLabel`, `chartYAxisLabel` map to anything in SwiftCrossUI. We have to build a chart layer ourselves on top of GtkBackend's `Path` widget. Estimated work: **3–4 weeks** for a usable subset (bar + line + sector, no animation, no per-point hit testing). The plan budgeted 3 weeks for this with a "simplify fidelity" escape hatch — that's still realistic if we narrow scope.
- **C2: `@FocusState` + `ScrollViewReader`.** Two structural building blocks SwiftCrossUI lacks. Both are core to `SessionDetailView` (autoscroll on new message; focused prompt input). Workarounds exist via GtkBackend `Widget` direct access plus a small SwiftCrossUI patch we'd carry locally. Estimated work: **3–5 days** if we vendor SwiftCrossUI (we will) and patch.
- **C3: `ViewThatFits` + custom `Layout` protocol.** 23 + 2 uses respectively. `ViewThatFits` is a layout-time fallback chooser; `Layout` is a custom-layout protocol. Both are absent. We either (a) replace `ViewThatFits` call sites with a hand-rolled `if/else` against view-width (we already use `GeometryReader`), or (b) port the minimal `Layout` protocol pattern into our SwiftCrossUI vendor patch. Estimated work: **1–2 weeks** if we go option (a) at every call site, or 3–5 days if we patch the framework. UsageView and Workflows are most affected.

**NO-GO would trigger if** any of these were also missing:
- `@State` / `@Binding` / `@Environment` / `@EnvironmentObject` — all present.
- `VStack` / `HStack` / `ZStack` — all present.
- `Button` / `TextField` — both present.
- `.task` / `.onChange` — both present.
- `.alert` / `.sheet` — both present.

None of those failure conditions hold, so **PROCEED**.

## Items to verify when Swift is installed locally

These ratings are based on SwiftCrossUI source-reading without a build. Real validation requires `swift build` against vendored SwiftCrossUI and trying the actual ports:

1. **`@SceneStorage → @AppStorage` substitution** — confirm the one usage in RootView.swift:8 still behaves correctly as app-scoped.
2. **`LazyVStack` performance** — confirm SwiftCrossUI's lazy layout actually defers rendering, or whether it eagerly materializes 100s of session entries.
3. **`PreferenceKey` reduce semantics** — SwiftCrossUI's PreferenceModifier may have different reduce/accumulate semantics than SwiftUI's.
4. **`Picker` style options** — confirm `MenuPickerStyle` renders as a Gtk drop-down on GtkBackend (vs. an inline list).
5. **`fileImporter` actual usage** — re-grep `fileImporter` across the full `Sources/` tree, not just `Views/`; SessionDetailView is suspected.
6. **Apple Charts subset feasibility** — prototype a single `BarMark` chart on top of `Path` to validate the declarative-DSL-over-Cairo approach.

These are the smallest set of "must validate before week 4" items.

## What happens to the original plan

The plan as written assumes Qt6Backend + QTermWidget. Substitutions required, all flagged in `spike/swift-cross-ui-decision.md`:

- "Qt6Backend" → "GtkBackend (Gtk4)"
- "QTermWidget" → "VTE 0.74+ (`libvte-2.91-gtk4`)"
- "Qt Charts 6" → "Custom chart DSL over SwiftCrossUI Path / Cairo"
- "qt6-qtbase-devel qt6-qtwayland-devel qt6-qtdeclarative-devel qt6-qtcharts-devel" → "gtk4-devel libadwaita-devel vte291-gtk4-devel cairo-devel pango-devel"
- Bundling: `linuxdeploy-plugin-qt` → `linuxdeploy-plugin-gtk`
- Threat T10 (clipboard X11/Wayland) unchanged; both backends honor the same Wayland data device.
- Branch-protection scope `Platform/Linux/` unchanged.
- AppImage size estimate stays in the ~180–290 MB band.
